# 性能对比：手机 vs 树莓派 5

测试时间 2026-09-27。工具：`tools/perf_matrix.py` (经主平台依次部署 4 种组合) + `tools/perf_sample.py` (两台设备同时每 2 s 采样) + `tools/precision_test.py` (精度) + `tools/bench_host.py` (单机基准)。

| 设备 | 配置 | 运行方式 |
|---|---|---|
| 板卡 | 树莓派 5，4 核 Cortex-A76 2.4 GHz，4 GB | Docker (agv-sim / agv-nav 镜像) |
| 手机 | Pixel 4，骁龙 855 (1×2.84 + 3×2.42 + 4×1.78 GHz)，6 GB，Android 13 | Termux + proot Ubuntu 22.04，proot 派生服务 |

同一车型 (单舵轮测试车)、同一场景 (九宫格立体仓 grid_9_square)、同一组 5 个目标、slam_toolbox 建图定位；每种组合分别用 Nav2 (RotationShim + RPP 线路跟随) 与自研导引各跑一遍。

## 1. 单机计算基准 (bench_host.py)

| 项目 | 手机 (proot 内) | 树莓派 5 |
|---|---|---|
| 纯 Python 单核循环 | 18.6 ms | 19.5 ms |
| numpy 400×400 矩阵乘 | 71.9 ms (Ubuntu 自带 numpy，无优化 BLAS) | 2.7 ms (pip numpy + OpenBLAS) |
| MuJoCo 物理一步 | 0.75 ms | 0.54 ms |
| 2D 激光一次扫描 (1638 束) | 1.37 ms | 1.16 ms |
| 3D 激光一帧 (6000 点) | 6.6 ms | 3.6 ms |
| 相机一帧 (射线渲染) | 152 ms | 179 ms |

单核算力两者相当；手机的优势是 8 核，但 proot 的系统调用转发有额外开销 (每次 stat/send 约 80~130 µs，原生约 3~4 µs)。

## 3. 结论

1. **推荐组合 C：手机跑仿真，板卡跑执行 (ROS 2 / Nav2 / slam_toolbox)**。板卡负载最低 (约 40%)，Nav2 横向偏差 34 mm，用时最短。
2. **手机不适合跑执行进程**：proot 下执行进程拿到状态只有 20~30 Hz，控制回路延迟大，Nav2 跟线偏差 236~316 mm；手机全包 (B) 时 slam_toolbox 也跟不上，定位误差可达 276 mm。
3. **树莓派的瓶颈是仿真把 4 核吃满**：同样的仿真在手机上约 120~140% CPU，在树莓派上 220~355%。当时推测是 OpenBLAS 多线程空转；实测主要原因是相机持续渲染，P0 优化后已降到 26~36% (见第 4 节)。
4. 各组合仿真实时因子都能保持 1.0。

实例 i11 (组合 C) 静置时的仿真内部指标：物理一步 3.3 → **2.0 ms**，三路激光一次扫描 12.8 → **4.9 ms**，相机不再成像 (之前 200 ms/帧持续渲染)；
手机 numpy 256×256 矩阵乘 3.5 ms (装 OpenBLAS 前约 75 ms/400×400)。

结论：
1. **CPU 大幅下降**：仿真在树莓派上从 200~355% 降到 26~36%，树莓派同时跑仿真和执行 (A) 时整机从 94% 降到约 50%；手机仿真进程从 136% 降到 65%。
   主要来自相机按需成像 (本地 A/B：同一仿真进程 190% → 11%)。
2. **状态频率接近 50 Hz 目标** (A、C 组 38~41 → 47~48 Hz)，因为仿真进程不再被相机渲染拖慢。
3. **精度没有明显变化**：A、C 组横向偏差 28~49 mm、终点误差 12~26 mm，与优化前在同一范围，仍然受定位 (slam_toolbox) 30~40 mm 的跳变限制；单次测试的波动大于这次改动的影响。
4. 执行放在手机上 (B、D) 依然不可用：D 组 Nav2 这次有 3 个目标失败并发生碰撞 (之前 5/5 但偏差 236 mm)，属于该组合本来的不稳定，不建议使用。
5. 手机 Web 网关绑到小核后 CPU 占用从 32% 升到 45~53% (小核慢，同样的工作占用时间更长)，但没有影响仿真；第二批 (P1) 会让网关空闲时不轮询。

## 6. 第二轮：仿真实时循环 C 化 + 推送流 (2026-09-28)

原则：MuJoCo / Nav2 / slam_toolbox / ROS 2 仍是基础引擎，只把包在引擎外面的 Python "壳"改成编译后的 C/C++ 代码运行。

| 部分 | 实现 | 开关 |
|---|---|---|
| 仿真实时循环 | `sim_core/native/simcore_rt.c`：定步长循环在**原生线程**里跑，不持有 Python GIL。循环内依次为：看门狗/急停/触边运动封锁 → 轮系运动学 → 轮地打滑 → 写控制量 → **`mj_step`** → 读位姿/接触 → 触边 → 光电 (**`mj_multiRay`**) → 编码器里程计 → IMU；2D 激光按各自频率用 `mj_multiRay` 扫描、加噪声/丢点、360° 融合，双缓冲输出。MuJoCo 通过 dlopen 使用 pip 包自带的 `libmujoco`，编译期头文件版本与运行期 `mj_version()` 不一致时拒绝启用，回退 Python 循环。Python (`sim_core/rt.py`) 只做配置、状态快照、行人移动、IO/事件、相机、3D 激光 | `SIM_RT=0` 回退 Python 循环；`SIM_LIDAR_RAY=engine` 激光走原 Python 路径 |
| 射线 | 光电/激光在 MuJoCo 后端**一律由 `mj_multiRay` 求交**；Python 线程里的调用也经 C 直接调 `mj_multiRay` (省掉 numpy 包装)。第一轮里自写的"MuJoCo 等价几何"已删除，自写线段求交只用于未安装 MuJoCo 的兜底后端 | — |
| 状态传输 | `GET /api/v1/stream`：一条长连接推送状态二进制帧 (50 Hz) + IO/光电 (20 Hz) + 2D 激光/融合扫描，替代执行进程的状态/IO/光电轮询和每帧一个请求的激光长轮询 (格式见 API.md 1.0) | `NAV_SIM_STREAM=0` |
| 速度指令 | UDP 通道 (与 REST 同号端口)：仿真侧由 C 实时循环的原生线程直接接收并写入指令，全程不经过 Python，替代 20~30 Hz 的 `PUT /api/v1/control/cmd_vel` | `SIM_CMD_UDP=0` / `NAV_CMD_UDP=0` |
| HTTP | `common/rest.py`：用逐行解析替换标准库基于 email.feedparser 的头解析 (服务端和客户端都生效)，Date 头按秒缓存 | `AGV_FAST_HEADERS=0` |
| 网关 | 最近 3 s 内没有网页/工具访问、也没有任务执行时，快照轮询从 20 Hz 降到 1 Hz | `GW_IDLE_POLL_S` |
| 执行进程 | `/api/v1/nav` 里的 `ros.graph()` 缓存 2 s | — |

一致性：`tests/test_sim_core.py` 共 22 项 (树莓派 sim 容器、本机均通过)，新增三项：
- C 实时循环单步与 Python `SimCore.step` 逐步一致：兜底后端和 MuJoCo 后端各 1100 步，含撞障碍物/触边/光电，位姿误差 < 1e-6；
- C 调 `mj_multiRay` 与 Python 绑定调用逐束一致 (200 个位置 × 721 束)；
- 激光/融合/里程计/开关量批量结果一致。

### 6.1 树莓派组合 A (i12)

| 运行 | 整机 CPU | sim_server | nav_runtime | C++ 桥接 | slam_toolbox | Nav2 合计 | 网关 | 物理一步 | 激光一轮 | 状态频率 |
|---|---|---|---|---|---|---|---|---|---|---|
| 基线 67c6eac | 46.1% | 34.1% | 50.5% | — | 29.7% | 42.3% | 8.7% | 1.54 ms | 3.61 ms | 48.5 Hz |
| 第一轮 (C 内核 + C++ 桥接) | 37.0% | 22.1% | 19.4% | 2.9% | 34.5% | 40.2% | 8.5% | 0.55 ms | 3.68 ms | 49.3 Hz |
| 第二轮 (实时循环 + 推送流) | 33.6% | 14.5% | 13.4% | 2.9% | 33.9% | 39.8% | 8.9% | 0.07 ms | 1.98 ms | 50.0 Hz |
| 第二轮 + UDP 指令 + 网关降频 | **33.9%** | **14.2%** | **12.6%** | 3.1% | 38.2% | 40.8% | 9.7% | **0.08 ms** | 2.03 ms | **50.0 Hz** |

- 整机 46% → 34%。**我们自己的两个进程** (sim_server + nav_runtime + C++ 桥接) 从 84.5% 降到 **29.8%**；剩下的大头是 slam_toolbox (约 35%) 和 Nav2 (约 40%)，这两个本来就是 C++ 引擎。
- 物理一步 1.54 → 0.08 ms (其中 `mj_step` 0.05 ms)，激光一轮 3.6 → 2.0 ms，RTF 保持 1.0。
- 最后一行里网关和 slam 略高：测试期间精度工具持续访问网关 (20 Hz 快照)，而 slam 与路线长度有关。网关降频只在无人访问时生效，这组测试体现不出来。
- 剩余热点 (py-spy)：仿真进程约 66% 的 GIL 时间在 HTTP 处理上，其中 JSON 编码 32% (主要是给网关的快照，测试期间 20 Hz)、推送流 15%；物理/激光的 Python 侧 (快照同步、取激光帧) 约 25%；执行进程约 57% 在推送流线程里 (解码加各个状态/激光回调，包括导航安全层和转发给 C++ 桥接)。

### 6.2 Nav2 线路跟随中断

测试中频繁出现的"Nav2 线路跟随中断 (ABORTED)"，查明有三个原因：
- slam_toolbox 的 TF 时间戳落后；
- 防护区挡住贴墙停车点，而且 Humble 的 FollowPath 反馈 `distance_to_goal` 不更新；
- Nav2 拒绝在贴墙位置原地转向。

旧版重试只是原样重发同一段路径，所以同一位置会连续失败 8 次。修复后改为：逐级调整位姿并从当前位置重新规划；Nav2 拒绝原地转向时由执行进程完成转向；连续 3 次无进展即放弃。详细分析见 [NAVIGATION.md](NAVIGATION.md)。

## 7. 复现

```bash
# 两台设备都接入同一主平台后，在手机 Termux 里:
python3 $PREFIX/var/lib/proot-distro/containers/ubuntu/rootfs/opt/agv/tools/perf_matrix.py \
    --hub http://<主平台IP>:<端口> --board-ssh <用户>@<板卡IP> --board-node <板卡节点名> --phone-node <手机节点名>
```
