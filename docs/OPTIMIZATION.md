# 底层运行优化方案 (树莓派 5 / 手机)

依据：`tools/perf_matrix.py` 四种组合测试 (2026-09-27，见 [PERFORMANCE.md](PERFORMANCE.md))，以及测试后在运行中的实例 i11 (手机仿真 + 树莓派执行) 上补充的线程级、接口级采样。
下文「已证实」表示有数据直接支撑，「推测」表示需要按第 4 节的方法验证。

> **进度**：第一批 (P0) 已实施并复测 (2026-09-27)：仿真 CPU 树莓派 200~355% → 26~36%、手机 136% → 65%，状态频率 38~41 → 47~48 Hz，精度不变。数据见 [PERFORMANCE.md 第 4 节](PERFORMANCE.md#4-p0-优化后复测-2026-09-27-下午)。
> R2 (OpenBLAS 线程) 没有单独 A/B：相机关掉后仿真 CPU 已降到 26~36%，剩余部分不再是瓶颈。下一步是第二批 (P1)。

## 1. 关键数据回顾

| 指标 | 树莓派 5 | 手机 (Pixel 4, proot) |

| 仿真进程 CPU (与执行同机) | 222% (A) | 117% (B) |
| 执行进程 nav_runtime CPU | 41~46% | 61~80% |
| slam_toolbox CPU | 26~58% | 21~88% |
| Nav2 各服务器合计 | ~40~45% | ~40% |
| proot 追踪进程 | — | 22~54% |
| 整机 | A: 94%、D: 95% (4 核跑满)；C: 36~42% | 200~372% / 800% |

i11 实时采样 (手机仿真)：物理步平均 **5.2 ms / 10 ms 步长** (基准只有 0.75 ms)，三路激光一次扫描 12.6 ms (3078 束)，相机 209 ms/帧且**持续渲染**；
树莓派执行进程已经拉取了 2131 帧相机图像 (经 WiFi)，但 ROS 里没有任何节点订阅相机话题。

## 2. 树莓派 5

### 2.1 问题与根因

| # | 现象 | 根因 | 依据 |
|---|---|---|---|
| R1 | 仿真在树莓派上时 4 核跑满，CPU 220~355% | **相机持续渲染**：`sim_server/service.py` 的 `_camera_loop` 不管有没有人取帧，都按 10 Hz 目标连续成像；一帧 7.7 万条射线，由 4 线程池 (`SIM_RAY_THREADS` 默认 min(4, 核数)) 并行，在 4 核机器上等于常驻吃满 1.5~2.5 核 | 已证实：单帧 179 ms、渲染无消费者判断；D 组 (树莓派只跑仿真) 355% |
| R2 | 同上 | pip numpy 自带 OpenBLAS，线程数默认等于核数，空闲等待时自旋 | 推测 |
| R3 | 执行进程白白消耗 CPU 和网络 | `nav_runtime/sim_link.py` 在启用 ROS 时总是拉取相机帧 (320×240×3 ≈ 230 KB/帧，经 WiFi)，再发布成 ROS 图像，没有订阅者 | 已证实：camera_frames=2131，话题列表无订阅 |
| R4 | nav_runtime 40~46% CPU，状态只有 35~41 Hz | 每 20 ms 一次 HTTP 短连接轮询 `/api/v1/state` + JSON 编解码；三路激光长轮询；相机拉取；Python 里做 ROS 消息序列化 (1440 束 LaserScan、TF)；这些都在一个带 GIL 的进程里争抢 | 已证实 (频率、CPU)；细分比例待剖析 |
| R5 | CPU 空闲时 Nav2 控制循环仍超时 (C 组 235 次) | 局部代价地图用 3 路激光 (两路 25 Hz 819 束 + 顶部 1440 束) 做障碍层射线清除，更新时持锁，控制循环查代价地图要等锁；RPP 碰撞检查也在同一循环 | 推测 (C 组 CPU 只有 40% 仍超时，排除 CPU 不足) |
| R6 | ROS 进程多、进程间序列化开销 | Nav2 8 个服务器各一个进程，同机也走 DDS 序列化 + UDP/共享内存 | 已知 |
| R7 | 系统本身有额外负载 | 树莓派跑着桌面环境 (lightdm、Xwayland) 和 NX 远程桌面服务，占约 250 MB 内存和少量 CPU | 已证实 (top) |

### 2.2 优化方案

| 优先级 | 方案 | 做法 | 预期收益 (预估) | 风险 |
|---|---|---|---|---|
| P0 | **相机按需渲染** (R1) | 仿真进程记录每路相机最近一次被取帧的时间，超过 2 s 没人取就停止成像；工作台打开相机页或有 ROS 订阅时才恢复 | 仿真 CPU 降 150~250%，树莓派整机从 95% 降到 40% 左右 | 低；首帧延迟约 1 帧 |
| P0 | **执行进程只在有订阅时拉相机** (R3) | `ros_bridge` 创建相机发布器后用 `get_subscription_count()` 判断，没有订阅者就不拉取、不发布；另加 `NAV_CAMERAS=0/1` 开关 | 执行进程 CPU 降约 5~10%，省 WiFi 带宽约 1~2 MB/s | 低 |
| P0 | **限制数学库线程** (R2) | 仿真/执行镜像设 `OPENBLAS_NUM_THREADS=1`、`OMP_NUM_THREADS=1`；`SIM_RAY_THREADS=2` | 若推测成立再降 50~100% | 低；需要 A/B 验证 |
| P1 | **CPU 分区 + 优先级** | Docker `--cpuset-cpus`：执行 (ROS) 用 0-1 核，仿真用 2-3 核；Nav2 controller_server、slam_toolbox 提高调度优先级 (`nice -n -5`，容器加 `SYS_NICE`) | 控制循环超时明显减少，跟线误差更稳定 | 中；同机时仿真可用核变少 |
| P1 | **局部代价地图减负** (R5) | 障碍层只用 360° 合并扫描 (10 Hz) 代替三路原始激光；局部代价地图 4 m×4 m；`update_frequency` 5 Hz | Nav2 超时降一半以上 (预估) | 低；障碍感知略慢 |
| P1 | **状态改为推送** (R4) | 仿真进程提供一条长连接 (分块传输或 WebSocket)，按物理步推送二进制状态 (struct 打包，约 200 字节)；激光合并到同一条流 | 状态稳定 50 Hz，执行进程 CPU 降约三分之一，控制延迟降 10~20 ms | 中；需改 sim_link 与接口 (保留旧接口兼容) |
| P2 | **Nav2 组合运行** (R6) | `nav2_launch.py` 用 `component_container_isolated` (`use_composition`) 把 8 个服务器放进一个进程，进程内零拷贝通信 | Nav2 合计 CPU 降 30~40%，内存省约 200 MB | 中；一个组件崩溃会带走整个 Nav2 |
| P2 | **系统精简** (R7) | `sudo systemctl set-default multi-user.target` 关闭桌面；不用的 NX、隧道服务停掉；CPU 调频设 `performance`；开 zram | 省约 250 MB 内存和几个百分点 CPU | 低；需要桌面时再切回 |
| P3 | 仿真镜像换 Python 3.11/3.12 | `python:3.12-slim` (MuJoCo 有对应 wheel) | 纯 Python 部分 (运动学、离散传感器) 快 10~25% | 低；需回归测试 |

## 3. 手机 (Pixel 4，Termux + proot)

### 3.1 问题与根因

| # | 现象 | 根因 | 依据 |
|---|---|---|---|
| M1 | 同样的程序在手机上更吃 CPU、延迟更大 | **proot 系统调用转发**：每次被拦截的系统调用 80~130 µs (原生 3~4 µs)；seccomp 过滤已启用 (Seccomp: 2)，只拦截与路径有关的调用，但 HTTP 建连/收发、文件访问仍被拦截。追踪进程本身占 22~54% | 已证实 |
| M2 | 物理步 5.2 ms/10 ms (基准 0.75 ms) | 物理线程与相机、激光、HTTP 服务线程抢 GIL；再加上线程会被调度到小核 (A55 1.78 GHz，性能约为大核的 40%) | 已证实：仿真进程线程在 5、5、0 号核之间迁移；步长数据 |
| M3 | 相机持续渲染，约占 1 核 | 同 R1 | 已证实：209 ms/帧 |
| M4 | numpy 矩阵运算比树莓派慢 27 倍 | 容器里是 Ubuntu 自带 numpy + 参考 BLAS (`libblas3`)，没有 OpenBLAS | 已证实 (gemm 75 ms) |
| M5 | 执行进程放手机上时状态只有 20~30 Hz，Nav2 跟线 200~300 mm | M1 (HTTP 轮询每次都有多次系统调用) + ROS DDS 走 UDP 回环 (每条消息都是系统调用) + 十几个 ROS 进程 | 已证实 |
| M6 | Web 网关 26~32% CPU (没人打开网页时也是) | 网关有自己的后台轮询 (快照、事件)，经 HTTP 访问仿真/执行进程 | 已证实 (CPU)；轮询细节待剖析 |
| M7 | 持续负载下降频 | 机身温度触发 Android 热管理 (热状态 3)，大核 2.4~2.8 GHz 降到 1.6 GHz | 已证实 |
| M8 | 内存紧张 | 5.6 GB 总内存只剩约 120 MB 空闲，已用 swap 680 MB；Android 低内存时会杀后台进程 | 已证实 |

### 3.2 优化方案

| 优先级 | 方案 | 做法 | 预期收益 (预估) | 风险 |
|---|---|---|---|---|
| P0 | **相机按需渲染** (M3) | 同树莓派 P0 | 仿真 CPU 降约 80~100% | 低 |
| P0 | **装 OpenBLAS** (M4) | 容器内 `apt install libopenblas0-pthread` (新装的已包含，现有手机补装)；`OPENBLAS_NUM_THREADS=2` | 矩阵运算快 10~25 倍 (影响内置 SLAM、相机/点云处理) | 低 |
| P0 | **绑大核** (M2) | 派生服务在 proot 外面加 `taskset`：仿真进程 (含其 proot 追踪进程) 绑 4-7 大核，网关、平台、代理放 0-3 小核；`~/.agv.env` 加 `AGV_CPUS_SIM=4-7` | 物理步回到 1~2 ms，RTF 更稳 | 低；只跑仿真时大核够用 |
| P1 | **减少系统调用** (M1/M6) | ① 仿真↔网关、仿真↔执行改用长连接推送 (同树莓派 P1)，省掉每次建连的 socket/connect/accept；② 网关在没有浏览器连接时停止后台轮询；③ 手机上可选「网关并入仿真进程」，去掉一跳 HTTP | 追踪进程开销降一半，网关 CPU 从 30% 降到 5% 以下 | 中 |
| P1 | **手机只当仿真节点** (M5) | 平台部署向导对手机节点默认只允许仿真角色 (节点类型设为「仅仿真」)，执行放板卡 | 避免最差组合 | 无 |
| P1 | **散热与供电** (M7) | 背夹风扇；充电到 80% 后停止 (或用直供电)；监测热状态，超过 2 时平台告警 | 持续性能提升 30~50% | 无 |
| P2 | **内存** (M8) | 手机只跑仿真时不需要容器里的 ROS 进程；关闭不用的应用；平台显示手机可用内存 | 减少被系统杀进程 | 低 |
| P3 | **仿真进程脱离 proot (研究项)** | 在 Termux 里用 clang 源码编译 MuJoCo 与 Python 绑定，Termux 原生 Python + numpy 运行 sim_server，彻底没有 ptrace 开销 | 仿真进程系统调用开销降到原生水平 (预估仿真 CPU 再降 30~40%) | 高；编译工作量大，需要验证 MuJoCo 在 bionic libc 下可用 |

## 4. 实施与验证

按优先级分三批，每批做完都用同一套方法复测 (第 1 节数据是基线)：

1. **第一批 (P0，约 1~2 天)**：相机按需渲染、执行进程按订阅拉相机、线程数限制、手机装 OpenBLAS、手机绑大核。
   验证：`perf_matrix.py` 重跑 A~D 四组；另做 A/B：同一组合分别设 `OPENBLAS_NUM_THREADS=1` 与默认，比较仿真 CPU，确认 R2。
2. **第二批 (P1，约 3~5 天)**：状态推送长连接、局部代价地图减负、CPU 分区与优先级、网关空闲不轮询、手机节点默认只跑仿真。
   验证：状态频率 ≥ 48 Hz、Nav2 超时告警次数、组合 C 的横向偏差。
3. **第三批 (P2/P3)**：Nav2 组合运行、系统精简、Python 版本升级；手机仿真脱离 proot 作为研究项单独评估。

需要补充的剖析 (做第二批前)：
- 用 py-spy 在树莓派容器里对 nav_runtime、sim_server 采样火焰图 (需要 `--cap-add SYS_PTRACE`)，确认 HTTP/JSON/ROS 序列化各占多少；
- 在手机上用 `strace -c` 的替代办法 (proot 下不能再 ptrace)：给 sim_server 加系统调用计数 (按接口统计请求次数与耗时)；
- 记录 Nav2 controller_server 每次循环耗时分布，确认 R5。

每项改动都保留开关 (环境变量)，默认值按测试结果决定；复测数据更新到 PERFORMANCE.md。
